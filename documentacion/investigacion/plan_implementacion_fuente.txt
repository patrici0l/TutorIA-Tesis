1. Propósito de este documento
Este documento define una ruta de desarrollo ordenada y reproducible para TutorIA-Lucero. Su objetivo es evitar que el proyecto crezca de forma desorganizada y asegurar que cada módulo se implemente sobre una base estable, segura, versionable y fácil de explicar durante la defensa.
El plan considera el stack ya definido para el proyecto: frontend con Angular, backend con Python y FastAPI, PostgreSQL con pgvector, arquitectura RAG, integración desacoplada con proveedores LLM, REST/OpenAPI, Docker para contenerización y Git/GitHub para control de versiones.
2. Principios de organización
Modularidad: Cada responsabilidad debe vivir en un módulo claro. No se mezclará autenticación, documentos, RAG, perfiles y generación en un mismo archivo.
API-first: TutorIA debe poder ser consumido por Angular y, posteriormente, por otros módulos de AdaptIA. Por eso la lógica principal estará disponible a través de una API REST versionada.
Separación de responsabilidades: Angular presenta la experiencia de usuario; FastAPI concentra la lógica; PostgreSQL persiste datos; pgvector soporta recuperación semántica; los proveedores LLM se conectan mediante una capa desacoplada.
Seguridad desde el inicio: Credenciales, claves, tokens y secretos nunca se escribirán dentro del código ni se subirán al repositorio.
Trazabilidad: Cada contenido generado debe poder relacionarse con el perfil utilizado, las fuentes recuperadas, el proveedor LLM, el modelo, la latencia, tokens y otros datos relevantes.
Desarrollo incremental: Primero se crea una base técnica estable. Después se implementan documentos, RAG, generación, personalización, métricas y evaluación.

12. Pipeline RAG
Carga del documento docente.
Validación del tipo de archivo.
Extracción y normalización del texto.
Segmentación del contenido en fragmentos.
Generación de embeddings.
Almacenamiento de embeddings y metadatos en PostgreSQL + pgvector.
Conversión de la consulta o necesidad del estudiante en una representación de búsqueda.
Recuperación de los fragmentos más pertinentes.
Construcción del contexto para el LLM.
Generación del recurso educativo y registro de las fuentes.
Antes de conectar el LLM se debe verificar que la búsqueda semántica recupera fragmentos correctos. Esto evita ocultar problemas de recuperación detrás de respuestas aparentemente buenas del modelo.
13. Perfil de rendimiento e integración externa
TutorIA no necesita calcular todas las notas o resultados académicos. Debe estar preparado para recibirlos desde otro módulo o aplicación mediante una API. Para las pruebas se podrán utilizar perfiles sintéticos controlados.
{
  "student_id": "EST-001",
  "topic": "limites",
  "performance": 42,
  "attempts": 4,
  "frequent_errors": ["limites_laterales"],
  "mastery_level": "low",
  "recommended_support": "reinforcement"
}
Variables útiles: desempeño por tema, número de intentos, errores frecuentes, tiempo de resolución, nivel de dominio estimado y tendencia de progreso.
14. Tipos de recursos educativos
La arquitectura debe permitir ampliar los tipos de recursos sin cambiar el núcleo. Se puede comenzar con un conjunto reducido y agregar otros de forma incremental.

15. Personalización
Desempeño alto: Retos, problemas de mayor complejidad y menor cantidad de explicaciones básicas.
Desempeño medio: Explicación breve, práctica guiada y quiz intermedio.
Con dificultades: Refuerzo de prerrequisitos, explicación paso a paso, pistas y quiz básico.
Dificultad localizada: Refuerzo únicamente en el concepto con mayor debilidad.

24. Seguridad mínima obligatoria
No exponer API keys en Angular.
No subir .env ni secretos_locales/.
Contraseñas almacenadas únicamente como hashes robustos.
JWT con expiración y mecanismo de renovación definido.
Validar MIME, extensión y tamaño de documentos.
Evitar ejecución de contenido subido por usuarios.
Validar y sanear entradas antes de persistir o enviar a proveedores externos.
Aplicar autorización por rol en endpoints sensibles.
Registrar errores sin guardar secretos ni contenido sensible en logs.
Limitar tamaño y frecuencia de solicitudes costosas a LLM.
Rotar inmediatamente cualquier secreto expuesto.
25. Definición de terminado para una funcionalidad
Una funcionalidad no se considerará terminada únicamente porque funcione en una prueba manual. Debe cumplir:
Endpoint o caso de uso implementado.
Validación de entrada y salida.
Lógica fuera del router/controlador.
Manejo de errores.
Persistencia cuando corresponda.
Prueba unitaria o de integración adecuada.
Documentación OpenAPI actualizada.
Frontend con estados de carga, éxito y error.
HTML, SCSS y TS separados en Angular.
Sin secretos ni datos sensibles en el commit.
Código revisado y commit descriptivo.
26. Experimentos previstos para la tesis
Experimento A: Generación directa del LLM frente a generación con RAG.
Experimento B: Mismo tema y recurso para perfiles de rendimiento alto, medio y bajo.
Experimento C: Comparación de OpenAI, Gemini y Claude bajo el mismo corpus, prompt y perfil.
Experimento D: Portabilidad entre Cálculo Diferencial y una segunda asignatura si el tiempo lo permite.
Las dimensiones de evaluación podrán incluir fidelidad a fuentes, pertinencia, adecuación de dificultad, calidad pedagógica, personalización, latencia, estabilidad, tokens y costo aproximado por generación.

28. Reglas para evitar desorden durante el proyecto
No crear carpetas nuevas sin una responsabilidad clara.
No duplicar lógica entre módulos.
No llamar directamente a proveedores LLM desde componentes Angular.
No mezclar consultas SQL dentro de routers.
No introducir una nueva tecnología si la actual resuelve el problema.
No implementar gamificación compleja antes de terminar RAG, personalización y trazabilidad.
No modificar el esquema de BD sin migración.
No fusionar una rama si rompe Docker, pruebas o la API.
No usar secretos reales en ejemplos, commits o documentación.
29. Resultado esperado de la arquitectura
Al finalizar, TutorIA-Lucero deberá ser un sistema modular en el que Angular gestione la experiencia de usuario; FastAPI exponga la lógica como servicios; PostgreSQL almacene información relacional; pgvector permita recuperar semánticamente los materiales docentes; RAG construya el contexto; los proveedores LLM generen recursos educativos; y el perfil de rendimiento determine cómo adaptar dichos recursos.
La arquitectura debe permitir que otro componente de AdaptIA envíe una necesidad de aprendizaje y reciba un recurso generado sin tener que conocer la implementación interna de TutorIA.
30. Regla final de prioridad
Primero estabilidad y trazabilidad; después complejidad visual y funcional. El proyecto debe avanzar de forma vertical: cada nueva capacidad debe funcionar desde la interfaz hasta la base de datos o proveedor correspondiente antes de iniciar la siguiente. Las animaciones, gamificación y mejoras visuales se incorporarán sin comprometer el núcleo técnico.
